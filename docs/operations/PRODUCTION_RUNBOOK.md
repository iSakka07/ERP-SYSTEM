# دليل نشر ERP-SYSTEM على Hostinger + Supabase

التطبيق Next.js يعمل على استضافة Node.js من Hostinger، وقاعدة البيانات PostgreSQL مُدارة على Supabase. SQLite تبقى للتطوير المحلي فقط، وتبدأ بيئة الإنتاج بقاعدة فارغة من دون استيراد بيانات أو مرفقات الاختبار.

## 1. إنشاء قاعدة Supabase

1. أنشئ مشروع Supabase جديدًا وفارغًا.
2. اختر منطقة قريبة من منطقة تطبيق Hostinger لتقليل زمن الاتصال، ثم اختبر الاتصال من بيئة التطبيق قبل الإطلاق.
3. من لوحة Supabase خذ رابط **Session pooler** لاستخدام التطبيق على Hostinger؛ هو مناسب لخادم Node.js مستمر ويدعم IPv4. استخدم Transaction pooler فقط إذا تحولت الاستضافة إلى serverless وبعد ضبط Prisma له.
4. خزّن كلمة المرور وروابط الاتصال كأسرار؛ لا تضعها في Git أو رسائل أو ملفات المشروع.

### حالة مشروع الإنتاج الحالية

- مشروع `ERP-SYSTEM` (`iuakqwojghfnekelczrr`) يعمل على PostgreSQL 17 في منطقة `eu-west-1`، وحجمه الحالي يقارب 14 MB.
- المشروع حاليًا على خطة Supabase Free. هذه مناسبة لاستكمال التجهيز والاختبار، لكنها ليست بوابة إطلاق لبيانات تشغيل حقيقية لأنها لا توفر النسخ الاحتياطية اليومية وقد يتوقف المشروع بعد فترة خمول.
- قبل فتح الموقع للمستخدمين الحقيقيين: رقِّ المشروع إلى خطة توفر نسخًا احتياطية يومية، أو فعّل تصديرًا خارجيًا يوميًا موثوقًا واختبر الاستعادة فعليًا. أي ترقية مدفوعة تحتاج موافقة منفصلة.

### السعة وخطة نمو المرفقات

| الخطة | سعة PostgreSQL المضمنة | سعة Supabase Storage المضمنة | ملاءمتها الحالية |
| --- | ---: | ---: | --- |
| Free | 500 MB | 1 GB | تجهيز واختبار فقط |
| Pro | 8 GB لكل مشروع قبل رسوم الزيادة | 100 GB | بداية مناسبة للإنتاج بعد اختبار الاستعادة |

النظام في نسخته الحالية يخزن المرفقات في أعمدة `BYTEA` داخل PostgreSQL. تقرر قبل الإطلاق نقل محتوى الملفات إلى Supabase Storage، والإبقاء في PostgreSQL على بيانات المرفق الوصفية فقط؛ لذلك الأرقام التالية تشرح الوضع القديم ولا تمثل التصميم المعتمد للإنتاج:

- 500 MB تستوعب نحو 10 ملفات بحجم 50 MB، أو 50 ملفًا بحجم 10 MB، أو قرابة 250 ملفًا بمتوسط 2 MB.
- 8 GB تستوعب نحو 160 ملفًا بحجم 50 MB، أو 800 ملف بحجم 10 MB، أو قرابة 4,000 ملف بمتوسط 2 MB.

### قرار معماري معتمد للمرفقات

- أنشئ bucket خاصًا باسم `erp-attachments` في Supabase Storage؛ لا يُسمح بروابط عامة دائمة.
- تظل صلاحيات النظام الحالية هي المرجع: الرفع والتنزيل والحذف تتم عبر مسارات الخادم بعد التحقق من جلسة المستخدم وصلاحياته.
- خزّن في PostgreSQL فقط: اسم الملف، نوعه، حجمه، اسم الـbucket، مسار الكائن، الجهة/السجل المرتبط، من رفعه، والتوقيت. لا تخزن بايتات الملف في قاعدة الإنتاج.
- استخدم مفتاح Supabase السري من الخادم فقط، ولا تضعه في متغير يبدأ بـ`NEXT_PUBLIC_` ولا ترسله إلى المتصفح.
- عند فشل حفظ سجل قاعدة البيانات بعد رفع الملف، احذف الكائن المرفوع تعويضيًا. وعند الحذف، سجّل العملية وتأكد من معالجة أي فشل بين Storage وPostgreSQL.
- روابط التنزيل تكون مؤقتة وموقعة، أو يمر التنزيل عبر الخادم؛ ولا يُكشف المسار للمستخدم دون فحص الصلاحية.
- نسخ PostgreSQL الاحتياطية لا تشمل ملفات Storage؛ لذلك يلزم نسخ واختبار استعادة مستقلان للمرفقات.
- لا تُنقل مرفقات SQLite أو Railway ضمن هذه المرحلة؛ يُعاد تقييمها عند اعتماد خطة نقل البيانات القديمة.

بوابة القرار قبل الإنتاج:

1. نفّذ Restore تجريبيًا ثم قرر الخطة؛ لا تتم أي ترقية مدفوعة تلقائيًا.
2. أكمل تحويل المرفقات إلى bucket الخاص واختبر الرفع والتنزيل والحذف وفشل العملية الجزئي قبل إدخال بيانات حقيقية.
3. أضف مراقبة عند 60% و75% و85% من سعة قاعدة البيانات، وراجع متوسط نمو الملفات شهريًا.
4. لا تعتمد على Free لتشغيل مالي طويل الأجل؛ حتى إن كانت السعة كافية مبدئيًا فهي لا توفر النسخ اليومية وتتعرض للتوقف بسبب الخمول.

## 2. أسرار وإعدادات Hostinger

أضف في إعدادات تطبيق Node.js على Hostinger:

- `DATABASE_URL`: رابط Supabase Session pooler مع SSL.
- `POSTGRES_DATABASE_URL`: رابط ترحيل بصلاحيات إنشاء/تعديل المخطط، إلى المشروع نفسه.
- `SUPABASE_PROJECT_REF`: القيمة `iuakqwojghfnekelczrr` للتحقق من أن رابط قاعدة البيانات يخص مشروع الإنتاج الصحيح.
- `SUPABASE_URL`: رابط API لمشروع Supabase، للاستخدام من الخادم فقط في تكامل Storage.
- `SUPABASE_SECRET_KEY`: المفتاح السري للخادم للوصول إلى Storage؛ لا يُرسل في المحادثات ولا يُكشف للمتصفح.
- `AUTH_URL`: رابط الإنتاج النهائي بصيغة HTTPS.
- `AUTH_SECRET`: سر فريد عشوائي بطول 32 حرفًا على الأقل.
- `BOOTSTRAP_ADMIN_NAME` و`BOOTSTRAP_ADMIN_EMAIL` و`BOOTSTRAP_ADMIN_PASSWORD`: لإعداد المدير الأول فقط عندما تكون قاعدة المستخدمين فارغة؛ تُسجّل العملية نهائيًا ولا تصلح لإعادة تعيين مدير موجود. احذف هذه المتغيرات من بيئة التشغيل بعد نجاح الدخول الأول.

يمكن مؤقتًا استخدام رابط واحد لـ`DATABASE_URL` و`POSTGRES_DATABASE_URL` عند التهيئة الأولى. لاحقًا يفضّل فصل مستخدم التطبيق عن مستخدم الترحيلات. مفتاح Supabase السري مخصص لعمليات Storage من الخادم، وليس بديلًا لكلمة مرور PostgreSQL.

## 3. تهيئة قاعدة الإنتاج الفارغة

نفّذ مرة واحدة من بيئة آمنة تملك الاتصال بـSupabase، بعد إعداد المتغيرات:

```powershell
pnpm install --frozen-lockfile
pnpm db:postgres:prepare
pnpm db:postgres:validate
pnpm db:postgres:generate
pnpm db:postgres:migrate
pnpm db:seed
pnpm db:accounting-setup
pnpm verify:production-env
```

شغّل `db:seed` من دون `ERP_SEED_DEMO=true`. يجهز الأدوار والصلاحيات والمخازن الأساسية وينشئ أول مدير فقط عندما لا يوجد مستخدمون. `db:accounting-setup` يجهز دليل الحسابات وحساب البنك. لا تشغّل `db:demo-setup` على قاعدة الإنتاج.

## 4. نشر تطبيق Next.js على Hostinger

- اختر إصدار Node.js 24 أو أحدث، بما يتوافق مع متطلبات المشروع.
- أمر البناء: `pnpm db:postgres:generate && pnpm build`.
- أمر التشغيل: `pnpm start`.
- لا تضع الترحيلات أو إنشاء المدير ضمن أمر البناء الذي يتكرر عند كل نشر. شغّل الترحيلات المراجعة والتهيئة الأولية مرة واحدة أو كخطوة إصدار منفصلة.
- احتفظ بـ`DATABASE_URL` و`AUTH_SECRET` في متغيرات البيئة على Hostinger، ولا تعرضها للمتصفح.
- التطبيق يستخدم تسجيل الدخول الحالي؛ ربط Supabase هنا لقاعدة PostgreSQL فقط، ولا يتطلب نقل المصادقة إلى Supabase Auth.

### خطوات Hostinger المعتمدة بعد إعادة تشغيل Codex

1. افحص وجود خطة Business Web Hosting أو Cloud صالحة لتطبيق Node.js، ولا تشترِ أو ترقِّ أي خطة دون موافقة منفصلة.
2. أنشئ تطبيق Node.js واحدًا بـNode 24، وانشر مصدر المشروع بأمر البناء `pnpm db:postgres:generate && pnpm build` وأمر التشغيل `pnpm start`.
3. اربط تطبيق Hostinger بمشروع Supabase الحالي `ERP-SYSTEM` عبر Database Connect Wizard، ثم تأكد أن `DATABASE_URL` يستخدم Session pooler على المنفذ 5432.
4. أضف `SUPABASE_PROJECT_REF=iuakqwojghfnekelczrr` و`AUTH_SECRET` و`AUTH_URL`، ولا تنقل ملف `.env` المحلي أو أسراره إلى Git.
5. اربط الدومين النهائي وشهادة HTTPS، ثم حدّث `AUTH_URL` إلى الرابط النهائي وأعد تشغيل التطبيق.
6. افحص `/api/health` وتسجيل الدخول بحساب المدير من رابط الإنتاج.

### اختبار القبول قبل فتح الموقع

1. نفّذ Restore تجريبيًا إلى قاعدة معزولة، وسجّل الزمن والنتيجة، ثم قرر Free أو Pro وفق السعة والنسخ المطلوبة.
2. اختبر إنشاء مستخدم محدود وتأكد أنه لا يستطيع فتح مسارات أو بيانات خارج صلاحياته.
3. اختبر إضافة مشروع، فاتورة شراء، استلامًا مخزنيًا، حركة خزنة/بنك، مستخلصًا ومرفقًا، ثم تحقق من ظهورها بعد إعادة تشغيل التطبيق.
4. تحقق من تنزيل المرفق والتقرير، ومن أن `/api/health` يرجع اتصال قاعدة البيانات الحقيقي.
5. خذ النسخة الافتتاحية بعد نجاح الاختبارات، واحتفظ بخطة رجوع قبل إدخال أول بيانات تشغيل فعلية.

## 5. النسخ الاحتياطي والاختبار قبل الإطلاق

- استخدم نسخ Supabase اليومية على خطة مناسبة للتشغيل، واحتفظ بتصدير مستقل خارج المشروع كذلك. جرّب استعادة فعلية إلى قاعدة اختبار؛ فحص ملف النسخة وحده ليس إثباتًا للاستعادة.
- ملفات المرفقات محفوظة في Supabase Storage وفق التصميم المعتمد ولا تدخل في نسخة PostgreSQL؛ انسخها واختبر استعادتها بشكل مستقل مع الحفاظ على تطابق مساراتها مع سجلات قاعدة البيانات.
- اختبر الدخول والأدوار وإضافة فاتورة واستلام مخزني جزئي وسداد مورد والمرفقات والتقارير، ثم راجع `/api/health` ويجب أن يرجع `{"status":"ok","database":"reachable"}`. أي فشل اتصال بقاعدة البيانات يرجع HTTP 503 دون كشف تفاصيل السر أو الخطأ.
- التطبيق حاليًا يعتمد على تشغيل نسخة واحدة بسبب بعض الحالة المحلية ومحددات محاولات الدخول؛ لا تشغّل أكثر من نسخة متزامنة قبل نقل هذه الحالة إلى خدمة مشتركة واختبارها.

## قبل كل إصدار

```powershell
pnpm db:backup
pnpm db:verify-backup
pnpm db:postgres:generate
pnpm db:postgres:migrate
pnpm verify:production-env
pnpm build
```

راجع SQL لأي migration جديدة قبل تطبيقها، ولا تعدّل migration سبق تطبيقها. `db:verify-backup` الحالي يفحص قابلية قراءة الأرشيف فقط؛ نفّذ استعادة فعلية إلى قاعدة منفصلة دوريًا.

## ما لا يزال يتطلب حساباتك

تم إنشاء وتهيئة مشروع Supabase `ERP-SYSTEM` (`iuakqwojghfnekelczrr`) مع المخطط وحساب المدير والبيانات الأساسية. لا يزال يلزم إنشاء تطبيق Hostinger بعد إعادة تشغيل Codex، وربطه بالمشروع، وإضافة أسرار التشغيل، ثم إجراء تجربة استعادة قبل فتح الرابط للمستخدمين. قاعدة SQLite المحلية لم تُحذف ولم تُستورد إلى الإنتاج.
