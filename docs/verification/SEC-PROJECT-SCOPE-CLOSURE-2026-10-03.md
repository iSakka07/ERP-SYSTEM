# SEC — نطاق المشروعات في صفحات الإنشاء

التاريخ: 2026-10-03

الحالة: **مغلق محليًا بعد اختبار قبول معزول.**

## المشكلة

كانت صفحات إنشاء الوارد والمقاولين والمشتريات تستعلم عن جميع المشروعات النشطة ثم ترسلها إلى المتصفح. كان API يرفض حفظ مشروع خارج نطاق المهندس، لكن أسماء المشروعات كانت تُكشف قبل الحفظ. كما أن رابط إنشاء مستخلص وارد كان يقرأ العقد بالمعرّف فقط، دون تطبيق نطاق المشروع في استعلام القراءة.

## الإصلاح

- صفحات `/incoming/new` و`/expenses/new` و`/purchases/new` تستخدم `projectWhere(user)` في استعلام المشروعات.
- صفحة `/incoming/[contractId]/statements/new` تقيد استعلام العقد نفسه بالنطاق، وتقيد قائمة المشروعات أيضًا.
- المستخدم المحدود الذي لا يملك تكليف مشروع يرى حالة فارغة واضحة ولا يستطيع إرسال النموذج من الواجهة.
- لم تتغير صلاحيات API أو migrations؛ كانت API بالفعل تتحقق من نطاق المشروع عند الحفظ، واختبار القبول يثبت استمرار ذلك.

## قبول الإصلاح

شُغّل:

```powershell
$env:ERP_TEST_ONLY = 'test:project-scope-acceptance'
pnpm test:isolated-api
```

ينشئ الاختبار قاعدة وخادمًا مؤقتين، ومستخدمًا من دور مهندس مكتب فني يملك صلاحيات إنشاء في الوارد والمقاولين والمشتريات ومكلّفًا بمشروع واحد فقط. ثم يتحقق من الآتي:

- كل صفحات الإنشاء تعرض المشروع المكلّف فقط ولا تسرب اسم أو معرّف المشروع أو العقد الآخر في HTML.
- رابط إنشاء مستخلص لعقد خارج النطاق يعيد إلى `/incoming` دون تحميل العقد.
- مستخدم لديه الصلاحيات نفسها دون أي تكليف مشروع يرى رسالة الحالة الفارغة في صفحات الإنشاء الثلاث ولا يحصل على قائمة كل المشروعات.
- طلبات API المباشرة للوارد والمقاولين والمشتريات خارج النطاق تفشل ولا تنشئ سجلًا.
- طلبات API داخل النطاق تنجح وتنشئ السجل.

النتيجة: نجح الاختبار كاملًا على بناء إنتاجي مؤقت في Next.js 16.3.8.

## تحقق إضافي

- `pnpm lint`: نجح دون أخطاء، مع 8 تحذيرات سابقة غير مرتبطة بهذا التغيير.
- بناء الإنتاج وTypeScript نجحا ضمن غلاف اختبار القبول.

## إعادة التحقق بعد النشر

بعد نشر الإصدار، اختبر حساب مهندس محدودًا على مشروع واحد: افتح صفحات الإنشاء الثلاث، وحاول فتح رابط إنشاء مستخلص لعقد تابع لمشروع آخر. يجب ألا يظهر المشروع الآخر في أي قائمة، ويجب أن يعيد الرابط إلى صفحة الوارد.
