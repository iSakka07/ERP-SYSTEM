# Product Bible — ERP-SYSTEM V1

## الغرض

منظومة عربية لشركة مقاولات «السلامة جروب» تربط المشروع من العقد والوارد إلى أعمال مقاولي الباطن، المشتريات، النثريات، الرواتب، البنك والقيود. هذه الوثيقة هي مرجع نطاق V1 داخل المستودع.

## تثبيت النسخة قبل الإطلاق — 2026-09-25

بناءً على قرار صاحب المنتج، النطاق الحالي هو آخر نسخة مرشحة قبل النشر، باسم **V1 Release Candidate**. هذا تثبيت لنطاق التسليم، وليس إعلان تشغيل فعلي أو شهادة اجتياز الاختبارات. يسمح بإصلاح عيوب النسخة والتحقق من التشغيل قبل اعتماد الإصدار؛ الإضافات الجديدة تؤجل لما بعد الإطلاق. لا يغير هذا القرار وحده تاريخ المحاسبة أو بيانات التشغيل أو رقم الحزمة البرمجي.

- آخر أساس مرفوع عند المراجعة: `081a9e1`. تعديلات تفاصيل سجل الإجراءات ما زالت في مساحة العمل ولم تدخل ذلك المرجع؛ يلزم استكمالها والتحقق منها قبل تثبيت مرجع التسليم النهائي.
- بعد بدء العميل إدخال بيانات حقيقية: لا تستخدم seed/demo أو إعادة ضبط القاعدة، ولا تعدل migration مطبقًا. التحديث يمر باختبار ونسخة احتياطية وخطة استعادة، والتصحيح المالي بعكس موثق.
- الإطلاق يسجل كتاريخ فعلي مستقل، مع مرجع Git المنشور ونتيجة اختبارات القبول واعتماد الأرصدة الافتتاحية. لم يسجل إطلاق فعلي بهذه المراجعة.
- نتائج المراجعة السريعة والفجوات وأولويات المعالجة: [مراجعة مرشح الإطلاق](./verification/RELEASE-CANDIDATE-2026-09-25.md).

### المحاسبة عند الإطلاق

تعرض الصفحة أرصدة افتتاحية معتمدة وحركات حقيقية لاحقة وتاريخ بدء ثابتًا. تبقى التفرقة بين الأرصدة التراكمية وحركة الفترة، وبين الاستحقاق والتحصيل، وبين التكلفة والصرف. الأرقام التجريبية لا تتحول تلقائيًا إلى أرصدة عميل.

السلوك الحالي: الترحيل يعمل دون تاريخ بداية؛ عند تحديده يتجاوز المستندات الأقدم منه. API يمنع تغيير التاريخ بعد وجود قيود إلا إذا كان مطابقًا للقيمة المسجلة، ويعيد معالجة مستخلصات ودفعات المقاولين فقط. لذلك يلزم قبل التسليم إجراء افتتاح معتمد واختبار تغطية كل الموديولات؛ زر التاريخ ليس ترحيلًا تاريخيًا شاملًا ولا يستبدل الأرصدة الافتتاحية.

الهدف بعد الإطلاق: عرض تاريخ التشغيل كحالة ثابتة، مطابقة الأرصدة مع دفاتر البنك والخزنة والموردين والمقاولين والجهات المالكة، وإقفال الفترات ومنع القيود بأثر رجعي داخلها. هذه متطلبات قبول، ولا تعد منفذة لمجرد ورودها هنا.

## الموديولات المعتمدة

| الموديول | مسؤوليته |
|---|---|
| الإدارة والمشروعات | الجهات، المشروعات، المهندسون والتسكين |
| الوارد | عقود الجهة المالكة، الجواري، شهادات الخامات والتحصيل |
| أعمال المقاولين | المقاولات، حصر الأعمال، الجواري، الخصومات والمدفوعات |
| المشتريات | فواتير وبنود شراء المشروع كتكلفة |
| المرتبات | الموظفون والتسكين وكشوف الرواتب والسلف والمكافآت والخصومات |
| Petty Cash | الصندوق التشغيلي، العهد، النثريات والمصروفات الصغيرة |
| البنك | حساب الشركة البنكي، التمويل والتحصيل والتسويات |
| المحاسبة | دليل الحسابات والقيود والفترات والأرصدة |
| موقف تكلفة المشروع | قراءة موحدة للإيراد والتكلفة والسيولة حسب المشروع |

## القواعد المالية الحاكمة

- العقد الوارد قيمة تعاقدية مرجعية؛ يتحول الاستحقاق والإيراد تدريجيًا مع المستخلصات.
- شهادة الخامات مستلمة من الجهة المالكة وملك للشركة محاسبيًا؛ تخصم نقدًا من المستخلص الذي ترتبط به وتظل تكلفة مواد للمشروع.
- مستخلص المقاول المعتمد ينشئ استحقاقًا للمقاول؛ الدفع يسوّي الاستحقاق ولا يكرر التكلفة. دفعات المقاولين من المدير التنفيذي/البنك، وليست من Petty Cash.
- Petty Cash صندوق تشغيل يومي. التمويل ليس إيرادًا، وتسليم العهدة ليس تكلفة؛ المصروف الفعلي فقط يحمل على المشروع أو العام.
- الرواتب ثابتة شهريًا، وتوزع تكلفة الموظف على المشروعات بحسب أيام الشهر الفعلية. الرواتب والمكافآت من المدير التنفيذي، لا من Petty Cash.
- كل مبلغ يخزن بالقروش، وكل حركة مالية حساسة داخل transaction، وبمفتاح idempotency. إعادة الإرسال ترجع النتيجة نفسها، والتشابه الحقيقي يحتاج تأكيدًا موثقًا.
- لا تحذف الحركة المالية المعتمدة؛ التصحيح يتم بعكس موثق ثم حركة بديلة عند الحاجة.
- الفترات المحاسبية المقفلة تمنع الترحيل والتصحيح بتاريخها حتى يعيد المحاسب فتحها بسبب موثق.

## الصلاحيات

- الواجهة تخفي ما لا يخص الدور، والخادم يطبق الصلاحية ذاتها لكل API.
- مدير النظام حساب تقني لإدارة الحسابات؛ المدير التنفيذي يرى أرقام الشركة ويعتمد/يصرف بحسب السياسة؛ المحاسب يدير الإدخال والاعتماد المحاسبي؛ ويوجد مهندس مكتب فني ومهندس مشرف.
- البيانات المالية في الرئيسية لا ترسل للحسابات التي لا تملك `project_cost_control.view`.
- حساب المهندس يرتبط بموظف وتكليفاته النشطة؛ لا يستقبل من الخادم إلا مشروعاته، ويمكن لمدير النظام تفعيل عرض الوارد وماليات المشروع له بصورة فردية.

## معيار إغلاق V1

1. `pnpm lint` و`pnpm build` ناجحان.
2. `pnpm test:isolated-api` ناجح على قاعدة مؤقتة، ولا يلمس قاعدة التشغيل.
3. النسخ الاحتياطي والتحقق منه قبل كل migration على بيانات العمل.
4. تشغيل العرض خلف HTTPS وبيئة منفصلة عن بيانات العميل.
5. لا يبدأ V2 أو استعمال مالي فعلي قبل مراجعة هذه الشروط مع صاحب العمل والمحاسب.

## خطة الاستضافة والتسليم

- نسخة Railway الحالية بيئة Demo مؤقتة للتدريب وليست اعتمادًا إنتاجيًا.
- النسخة الحقيقية للعميل تكون مستقلة، بقاعدة بيانات ومخزن مرفقات ونسخ احتياطية منفصلة، مع بيئتي Staging وProduction.
- تظل إدارة الكود والنشر والأسرار والبنية التحتية تحت سيطرة المالك التقني وفق عقد الترخيص والدعم، بينما تظل بيانات التشغيل والمستندات ملكًا للعميل.
- مشاركة رابط النظام لا تمنح وصولًا؛ الحماية تعتمد على الحسابات الفردية والصلاحيات ونطاق المشروع والجلسات وسجل التدقيق.
- التفاصيل التنفيذية ومراحل التحويل إلى الإنترنت موثقة في [خطة استضافة وتسليم العميل](./operations/CLIENT_HOSTING_CONTROL_PLAN.md).
